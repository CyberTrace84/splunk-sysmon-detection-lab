## 1. Summary
The detection fired on 10 failed logon attempts for the account `fakeadmin`
within about 75 seconds, which matches a password-guessing pattern.

## 2. Evidence
- **Event ID:** 4625 (An account failed to log on)
- **Failures:** 10 between 08:12:51 and 08:14:04 UTC
- **Logon type:** 3 (network)
- **Failure reason:** Unknown user name or bad password, sub-status 0xC0000064
- **Source:** ::1
- **Screenshots:** `screenshots/01-failed-logons-events.png`,
  `screenshots/06-alert-triggered-after-tuning.png`

## 3. Analysis
1. **Does the account exist?** No. Sub-status 0xC0000064 means the user name
   does not exist, and `fakeadmin` is not a real account on this host. Guessing
   passwords against a non-existent name is typical of username enumeration or
   automated spraying.
2. **Where did it come from?** The source was `::1`, the loopback address, so
   the attempts came from the host itself. In a real incident, an external or
   unexpected internal address would raise the severity.
3. **Pattern:** same account, same logon type and a regular interval of about
   8 seconds between attempts, which suggests a script rather than a person
   mistyping.
4. **Did any logon succeed?** I searched Event ID 4624 for the same period and
   found no successful logon for `fakeadmin`. This is expected, since the
   account does not exist.
5. **Other accounts targeted:** only `fakeadmin` appears in the failures for
   this period.

## 4. Verdict
**True positive for the technique, not a real incident.** The detection works
as designed. With a non-existent account, no successful logon and a local
source, I would classify it as low risk in production.

## 5. Escalation decision
**Not escalated** in this case. I would escalate to L2 if:
- a successful logon (4624) followed the failures from the same source;
- the targeted account was real or privileged (for example Administrator);
- the source was external, or one source targeted many accounts;
- the activity continued after the first alert or spread to other hosts.

## 6. Recommended actions (if this were real)
- Identify the source system and its owner; block or isolate it if unauthorised.
- Check the target account for lockouts and unexpected successful logons.
- If a real account was targeted, force a password reset and review its recent
  activity.
- Check whether the same source attempted other hosts.

## 7. Detection notes
- Expected false positives: users repeatedly mistyping a password, and
  services with an outdated stored password.
- Tuning history: the first version fired 11 duplicate alerts for one test.
  It now uses a 10-minute lookback and suppresses repeats per user for 30
  minutes.
